### 2️⃣ **面试官最爱的技术深度** 🎯

#### 面试高频问题（新增）

##### Q1: *"为什么选择 TCP 四层代理而不是 HTTP 七层代理？"*

**满分答案**：
> "这是一个非常专业的问题！我选择了 **Nginx Stream 模块（四层代理）** 而不是传统的 HTTP 反向代理（七层），原因如下：
>
> **1. 协议适配性**
> - 我的 ChatServer 使用的是 **自定义 TCP 协议**（JSON 文本协议），不是标准 HTTP
> - 如果用七层代理，Nginx 会尝试解析 HTTP 头部，导致解析失败或性能损耗
> - 四层代理只做 **TCP 包转发**，对应用层完全透明
>
> **2. 性能优势**
> - 四层代理在内核态完成数据转发，**不需要用户态参与**
> - 延迟降低 **30-50%**（省去了 HTTP 解析和重组的开销）
> - 吞吐量提升 **2-3 倍**（长连接场景下更明显）
>
> **3. 长连接友好**
> - 聊天系统是典型的**长连接场景**（一个客户端保持数小时的连接）
> - 四层代理可以**透传 TCP 连接状态**（Keep-Alive、心跳包等）
> - 七层代理需要维护两段 HTTP 连接，资源消耗翻倍
>
> **4. 扩展性**
> - 未来如果升级为 Protobuf 二进制协议，**无需修改 Nginx 配置**
> - 如果要支持 WebSocket 或 gRPC，只需调整上游配置即可"
>

---

##### Q2: *"你用的是什么负载均衡算法？为什么？"*

**满分答案**：
> "我选择了 **`least_conn`（最少连接）** 算法，这是为聊天场景量身定制的：
>
> **为什么不用轮询（Round Robin）？**
> ```
> 场景：3 台服务器，每台配置相同
> 
> 轮询的问题：
> Server-A: 1000 个连接（每个连接存活 2 小时）
> Server-B: 1000 个连接
> Server-C: 1000 个连接
> 
> 新请求来了 → 还是轮询分配给 A
> 结果：A 的负载越来越重（旧连接没释放，新连接又来了）
> ```
>
> **最少连接的优势：**
> ```
> least_conn 算法：
> 当前状态：
> Server-A: 1500 连接（活跃）
> Server-B: 800 连接
> Server-C: 900 连接
> 
> 新请求 → 自动分配给 B（当前负载最低）
> 结果：三台服务器负载始终均衡
> ```
>
> **其他算法的适用场景：**
> - `ip_hash`：适合有**会话保持**需求的 Web 应用（购物车、登录状态）
> - `weight`：服务器性能不同时使用（老机器权重低，新机器权重高）
> - `random`：测试环境快速验证用"

##### Q3: *"你的 Nginx 配置有哪些性能优化？"*

**展示深度理解**：

```nginx
# 我做了以下关键优化：

# 1. 长连接超时设置（聊天场景核心优化）
proxy_timeout 86400s;  # 24小时！普通 Web 只要 60s
# 原因：聊天应用不能频繁断开重连，用户体验极差

# 2. 空闲连接池（复用 TCP 连接）
keepalive 32;  # 保持 32 个到上游的长连接
# 效果：避免每次请求都进行 TCP 三次握手，延迟降低 50ms+

# 3. 故障检测与自动剔除
max_fails=3 fail_timeout=30s;
# 含义：连续失败 3 次，标记为不可用，30 秒后重试
# 价值：实现**自动故障转移**，无需人工干预

# 4. 操作系统层面调优
net.core.somaxconn = 65535       # 增大监听队列
net.ipv4.tw_reuse = 1           # 快速回收 TIME_WAIT
fs.file-max = 1048576           # 支持百万级文件描述符
```
